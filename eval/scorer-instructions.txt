You are scoring open-source pull requests against a fixed rubric. Apply the rubric exactly as written. The outcome of each pull request (merged or closed) is hidden and must not be guessed or used.

# Pull request rubric (fixed 2026-10-21 before any scoring)

Source: the questions document (`QUESTIONS.md`) and its `SKILL.md` digest. Distilled into 13 yes/no questions that can be judged from what a pull request
exposes publicly: title, body, linked issue references, the file list with line counts, the diff
where small, the CI check summary on the final head, and the discussion before the close.

Scorer instructions (identical for both models):

- Judge each question from the material given only. Do not guess about anything not shown.
- Answer each question with exactly one of `P` (pass), `F` (fail) or `NA` (not applicable).
- When the evidence is ambiguous and the fail condition is not clearly met, answer `P`. A fail needs
  a visible reason.
- The outcome (merged or closed) is not shown and must not be inferred or used.
- Line counts: "changed lines" means additions plus deletions. "Hand-written lines" excludes files
  that are plainly generated, vendored third-party code, test data, binary assets, translations, or
  documentation XML regenerated by a tool, when the material identifies them as such.

## The questions

**Q1. Wanted.** Does the PR show the change was wanted before it was written?
- P: links or references an issue, proposal, or prior discussion that asks for this change; or a
  maintainer asked for it; or the change is trivial (a typo, a comment, an obvious one-line crash or
  build fix) where an issue first is not expected.
- F: a non-trivial new feature, behaviour change or refactor with no linked issue, proposal or prior
  discussion, or the discussion shows the project had already decided against it.
- NA: never (every PR is either trivial or not).

**Q2. Problem stated.** Does the title or body say what problem it solves (what breaks, or what
user need it meets), rather than only what was changed?
- P: the problem is stated in the PR, or the PR links an issue that states it.
- F: the body is empty or only restates the change, and no linked issue supplies the problem.
- NA: never.

**Q3. Cause stated.** For a bug fix, does the PR or its linked issue name the cause (why it
happens), not only the symptom (what is seen)?
- P: a causal explanation is given ("X happens because Y"), or the diff is self-explanatory at a
  glance (for example, an off-by-one or a missing null check visible in a few lines).
- F: a bug fix that names only the symptom and a non-obvious change, with no cause.
- NA: the PR is not a bug fix (feature, docs, refactor, style, tests).

**Q4. Not a symptom patch.** Does the fix avoid managing the symptom: raising a limit or
timeout, suppressing or silencing a warning or error, adding a catch or guard that hides the failure,
or special-casing the one reported input, without saying why that is the right fix?
- P: the change addresses a mechanism, or a containment change is justified in the body.
- F: the diff visibly suppresses, silences, raises a number, or special-cases one input, and the
  body does not justify it; or the discussion shows a reviewer identified it as a workaround.
- NA: the PR is not a fix (feature, docs, refactor, style, tests).

**Q5. Right layer.** Does the change sit at the right place: not working around a problem
owned by a dependency, a lower layer or another component, and not adding a new path where an existing
one would serve?
- P: no sign of the change belonging elsewhere.
- F: the body or discussion shows the change works around a problem in another layer or dependency,
  duplicates an existing mechanism, or a reviewer says it belongs elsewhere.
- NA: never.

**Q6. Proportionate cost.** Is the permanent cost proportionate: no new third-party dependency,
no new permanent machinery (an option, a setting, a CI job, a subsystem) out of proportion to the
problem stated?
- P: no new dependency, and any new machinery is proportionate to a stated problem.
- F: adds a third-party dependency, or adds a setting, option, CI job or subsystem for a problem that
  is rare, unstated or minor, or a reviewer questions whether it is worth carrying.
- NA: never.

**Q7. Behaviour change explained.** If the PR changes existing behaviour users may rely
on, removes something, or changes a default, does it say so and why?
- P: the change is named and justified.
- F: existing behaviour, a default, or a public API is changed or removed without saying so or why.
- NA: the PR changes no existing behaviour (pure addition, pure bug fix restoring documented
  behaviour, docs, tests, internal refactor with no visible change).

**Q8. Evidence it was run.** Does the PR show the change was run or tested?
- P: adds or updates tests, or the body shows output, screenshots, a video, a benchmark, or concrete
  steps the author ran with the result.
- F: a code change that alters behaviour with no tests and no evidence of having been run.
- NA: documentation, comments, translations, CI configuration or pure formatting with no behaviour.

**Q9. CI green.** Did the CI checks on the final head pass?
- P: all reported checks succeeded (skipped or neutral checks count as passing), or failures are
  shown in the discussion to be unrelated to the change.
- F: one or more checks failed or were cancelled on the final head, with no sign they are unrelated.
- NA: no checks were reported for the final head (unknown, not clean).

**Q10. Reviewable size.** Is the hand-written change a reviewable size?
- P: 150 hand-written changed lines or fewer; or larger, with the body explaining why it cannot be
  split (for example, generated code declared, or a maintainer asked for it whole).
- F: more than 150 hand-written changed lines with no such explanation.
- NA: never.

**Q11. One concern, its purpose only.** Is the PR scoped to one concern, touching only what its
stated purpose needs?
- P: every changed file plausibly serves the one stated purpose.
- F: unrelated changes ride along (drive-by refactors, reformatting of untouched code, unrelated
  files, stray build or editor artifacts), or the PR bundles several separate problems.
- NA: never.

**Q12. No generated filler.** Is the write-up free of filler and unverifiable claims:
no unfilled template, no long generic boilerplate, no claims the diff does not support, and generated
code (if any) declared?
- P: the write-up is specific to this change, or short and accurate.
- F: unfilled template placeholders, long generic prose that could describe any change, claims that
  the diff plainly does not support (a file, test, or behaviour that is not in it), or a large
  generated change not declared.
- NA: never (an empty body is P here; emptiness is judged by Q2).

**Q13. No duplicate.** Is there no sign the change duplicates an existing open or merged
PR, an existing feature, or a fix already on the main branch?
- P: no sign of a duplicate in the material.
- F: the body or discussion shows the change duplicates an existing PR, an existing feature or a fix
  already made.
- NA: never.

## Derived measure

A PR "fails at least one question" when any of Q1 to Q13 is `F`. NA and P do not count as fails.

## Output format

For each pull request in the message, output exactly one line, in the order given:

<ID> Q1 Q2 Q3 Q4 Q5 Q6 Q7 Q8 Q9 Q10 Q11 Q12 Q13 | <for each F, the question number and a reason of at most 12 words, separated by semicolons; or "none">

Each Q value is P, F or NA. Example:
G999 P F NA NA P P NA F NA P P P P | Q2 body only restates the change; Q8 behaviour change, no tests or run evidence

Output nothing else: no preamble, no summary.
